# Exact swap eligibility

The ring-map selector needs two answers: whether a first node has any legal
partner, and whether a particular pair can be exchanged. Protection is pointwise
at the completed sequence boundary. Other unheld nodes may move; this is not an
isolated transposition. Eligibility does not find or optimize a move sequence.
The existing constrained solver remains responsible for producing and verifying
the sequence after a pair is selected.

Let `d` be the number of model addresses, `G` the group generated by legal moves,
and `F` the currently held addresses. Define

\[
H=\{g\in G:g(f)=f\text{ for all }f\in F\}.
\]

For distinct occupied unheld addresses `a,b`, a swap is feasible exactly when

\[
(b,a)\in H\cdot(a,b).
\]

The computation therefore explores **ordered-pair orbits**, not complete puzzle
configurations. Ordinary point-orbit membership is only a necessary condition:
a three-cycle can move `a` to `b` without exchanging the two.

## Exact stabilizer construction

The existing complete full-solve cache supplies certified base orbit sizes and
legal representatives. A bottom-up pass extracts a compact strong generating
set without expanding move words. Held nodes are promoted to the base prefix
using adjacent base swaps, keeping their previous relative order to minimize
the number of swaps. Filtering generators that fix this prefix gives `H`.

For an adjacent pair `a,b`, let `K` fix the earlier prefix and let
`L=K_(a,b)`. The old base gives the indices `r=[K:K_a]` and
`s=[K_a:L]`. An orbit of `b` determines `t=[K:K_b]`, so the exact
target size of the orbit of `a` under `K_b` is `rs/t`.
Schreier generators fixing `b` are added until that size is reached. The
constructed subgroup already contains all of `L`; reaching the certified index
therefore proves that it is the entire `K_b`. Deeper stabilizers are retained.
Periodic strong-generator compaction uses the same index argument.

For every resulting point orbit, a breadth-first traversal of ordered pairs
tests reversal reachability. A negative answer is published only after that
entire ordered-pair orbit has been explored. Different point orbits also prove
a pair impossible immediately. These deductions stay valid if a later budget
limit interrupts the computation.

## Backend and worker contract

```js
const analyzer = new EligibilityAnalyzer(model, completeFullSolveCache);
const result = analyzer.analyze({
  protected: heldAddresses,
  occupiedNodes: currentPhysicalAddresses,
  protection: 'endpoint'
}, {maxMs: 3000});

eligibilityStatus(result, a);    // first-node eligibility
eligibilityStatus(result, a, b); // selected pair eligibility
```

The helper returns `0` for unknown, `1` for feasible, and `2` for proved
infeasible. Unknown nodes must remain available in the UI. A complete result
classifies all candidate pairs. A partial result contains both proven results
and unknown pairs; `invalid` input or unavailable data provides no new negative
claim. `throughout` protection is also supported and uses only primitive moves
fixing all held nodes, matching the existing strict mode.

The browser request is:

```js
{
  task: 'eligible-swaps', id, modelId, snapshot,
  selection: {protectedStickerIds: [...]},
  options: {maxMs: 3000}
}
```

The worker maps physical sticker IDs from the current snapshot to addresses.
It never mutates a puzzle. The reply includes `modelFingerprint`, plus a result
with `degree`, `protectedNodes`, `occupiedNodes`, `candidateNodes`,
`firstStatus`, `knownPairs`, `feasiblePairs`, `status`, and `stats`.
`firstStatus` is a `Uint8Array(d)`. The other two arrays are packed bitsets:
bit `a*d+b` indicates whether the pair is known and, if known, feasible.
An unset known bit always means unknown. Empty geometric addresses, held
nodes, and same-node pairs are unavailable endpoints. Model and chain assets
are loaded lazily and verified against their build fingerprints.

## Cost and limits

If `s` is the current generator count, pair traversal costs at most `O(s*d^2)`
transitions, often much less because the puzzle has many small point orbits.
It stores `O(d^2+s*d)` transient scalar entries. Adjacent base reordering is
data dependent and bounded separately; it does not enumerate `|G|` states.

The browser caps each analysis at 3 seconds, 100 million counted operations,
50,000 adjacent base swaps, 2,000 strong generators, and a 48 MiB working-storage
estimate. Timing and storage checks are cooperative estimates, not a hard
process-memory guarantee. Resource limits return unknown for unresolved pairs.
Only complete results are cached, with a 2 MiB result-cache limit. The largest
current result (`d=294`) uses about 22 KiB for the three typed arrays. No new
precomputed puzzle tables or dependencies are shipped.

On the development runner, all 28 actual engine models completed with no holds,
one non-prefix hold, and approximately 20% spread-out holds. The 7×7 cube took
about 0.52 seconds for 59 held nodes, 0.77 seconds for 147, and 0.41 seconds for
220; its peak accounted working storage was about 7.6 MB. These are sample
measurements, not a worst-case or device-speed guarantee.

## Validation

`solver-backend/tests/eligibility.test.cjs` compares every held subset and every
pair with exhaustive independent group enumeration for nine tiny groups,
including cyclic, alternating, symmetric, and coupled-swap cases. It checks
endpoint versus throughout semantics, physical occupancy, budget cutoffs, and
cache isolation. `tests/eligibility-worker.test.cjs` exercises all 28 actual
engines after moves, held-node mapping, typed arrays, lazy cache loading,
fingerprints, corruption rejection, invalid input, and resource limits.
